# Debian OpenSSL weak-key screen of the pinned Patoshi public keys

**Status:** bounded screen. Results and completion time are recorded in [result.json](result.json); the machine-readable validation receipts are in [validation.json](validation.json), with file hashes in [manifest.json](manifest.json). The population is the 21,953 uncompressed public keys in `patoshi_pubkeys_COMPLETE.csv`. Labels: **(a)** directly verified source/code/data fact; **(b)** inference from specified evidence; **(c)** speculation. No identity claim follows from this screen.

## 1. Corpus search

**(a)** The [Debian DSA-1571 advisory](https://www.debian.org/security/2008/dsa-1571) dates the vulnerable package to September 17, 2006 and the repair to May 2008. It concerns key *generation on vulnerable software*, so the dates of these 2009–2010 public keys alone cannot exclude a vulnerable installation that was never patched. The defect disabled input mixing in `RAND_add`, not just an output-buffer mix; see [Debian bug #363516](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=363516), the [historical Debian patch discussion](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=363516#76), the [later, repaired `valgrind.patch`](https://sources.debian.org/patches/openssl/0.9.8o-4squeeze23/valgrind.patch/) and the [reconstructed vulnerable patch](https://github.com/CVE-2008-0166/key_generator/commit/c39d4c0e82879314f0a44e55f0212bd12c291e3e). The original 2006 SVN diff is cited in the Debian bug but its old server was unavailable; the reconstructed diff and published vectors independently constrain the implemented behavior.

**(a)** The documented [badkeys/debianopenssl corpus](https://github.com/badkeys/debianopenssl) (inspected at `c3412fddd03438fffc0f466ed52bfbb9ddc43a1a`) has RSA, DSA and EC on NIST P-256/P-384, with later P-521 files; it has no secp256k1 branch. Its own README describes PID, architecture and `.rnd` variation. The [CVE-2008-0166/private_keys](https://github.com/CVE-2008-0166/private_keys) and [key_generator](https://github.com/CVE-2008-0166/key_generator) projects likewise publish or generate NIST curves rather than a reusable complete secp256k1 corpus. The [Debian `openssl-blacklist` manual](https://manpages.debian.org/testing/openssl-blacklist/openssl-vulnkey.1.en.html) covers RSA/DSA blacklists; those keys cannot be intersected directly with Bitcoin EC points. [“Mining Your Ps and Qs”](https://factorable.net/paper.html) is RSA/DSA-oriented. [Bos et al., 2014](https://fc14.ifca.ai/papers/fc14_submission_158.pdf) describe generating Debian-weak secp256k1 keys for a Bitcoin analysis, but do not publish a documented, reusable complete corpus. A [secp256k1 generator repository](https://github.com/demining/Vulnerable-to-Debian-OpenSSL-bug-CVE-2008-0166) (inspected at `8198f6c123b7f8a453a2094384fdbbac20574796`) exists, but it is code, not a complete documented enumeration with validation coverage. **(b)** From these searched sources, no complete, documented secp256k1 corpus suitable for a direct intersection was found. This is a search result, not a claim that none exists anywhere.

## 2. Source-grounded model and validation

**(a)** [OpenSSL 0.9.8c `md_rand.c`](https://github.com/openssl/openssl/blob/OpenSSL_0_9_8c/crypto/rand/md_rand.c) keeps a 1,023-byte state, a SHA-1 digest, and two native `long` counters. Its `RAND_add` uses 20-byte state chunks; the Debian defect removes `MD_Update(&m,buf,j)` from that input path. The `RAND_bytes` loop hashes the native four-byte `pid_t` in the **first 10-byte output chunk of each call** (when nonzero), plus the digest, counters and state. The code deliberately models PID as four bytes, in native little or big endian; it does *not* treat PID as a one-time initial seed. The two-byte-order model also encodes the native `long` counters and the `time_t` added before each BN draw at their 32- or 64-bit native widths. External values supplied to vulnerable `RAND_add` are absent, but each call's byte **length** still advances state. The source model is in [debian_weak_screen.py](../../../scripts/debian_weak_screen.py).

**(a)** [OpenSSL 0.9.8c `rand_unix.c`](https://github.com/openssl/openssl/blob/OpenSSL_0_9_8c/crypto/rand/rand_unix.c) explains the `RAND_poll` sequence: 32-byte urandom read and three native-long additions. [Its `bn_rand.c`](https://github.com/openssl/openssl/blob/OpenSSL_0_9_8c/crypto/bn/bn_rand.c) calls `RAND_add(time_t)` and then `RAND_bytes` in `BN_rand`; `BN_rand_range` retries out-of-range draws. [Its `ec_key.c`](https://github.com/openssl/openssl/blob/OpenSSL_0_9_8c/crypto/ec/ec_key.c) has `EC_KEY_generate_key → BN_rand_range`. In [archived Bitcoin v0.1.0 `key.h`](https://github.com/Fiach-Dubh/bitcoin-0.1.0/blob/master/key.h), `CKey::MakeNewKey` selects secp256k1 and calls `EC_KEY_generate_key`; [v0.1.0 `main.cpp`](https://github.com/Fiach-Dubh/bitcoin-0.1.0/blob/master/main.cpp) calls it at miner startup and after found blocks. **(b)** Thus 16 consecutive `CKey::MakeNewKey`-like keygens per process form a defensible bounded offset window. This is a model of a vulnerable Linux/OpenSSL path, not evidence that the actual miner ran it. The archived client source also has Windows-specific entropy calls, and an unknown custom miner could differ.

**(a)** Before screening secp256k1, the model reproduced the **private scalar and public point** of nine independently published Debian weak P-256 PEM keys, PID 1: little-endian 64-bit, little-endian 32-bit and big-endian 32-bit, each under three published OpenSSL command-line startup variants. Every PEM was SHA-256-pinned before loading. [Validation receipts](validation.json) give each source URL, PEM digest, public X and two equality results. This exercises PID byte order, native-long width, `RAND_poll`, `RAND_add` length effects, `.rnd` loading and `BN_rand_range` behavior. The `struct stat` call lengths (144 bytes on le64; 88 on le32/be32) were inferred as the **unique** lengths in a 1–256-byte search reproducing those vectors, rather than presumed from the host ABI. The optional 64-bit big-endian branch has no published vector; its two startup paths are explicitly exploratory.

**(a)** The published [badkeys README](https://github.com/badkeys/debianopenssl) says CLI keys differ with a 1,024-byte `.rnd` file and across old/new no-`.rnd` OpenSSL behavior. The [0.9.8c `randfile.c`](https://github.com/openssl/openssl/blob/OpenSSL_0_9_8c/crypto/rand/randfile.c) adds `struct stat` even when `stat` fails; later behavior removes that failed-stat call. The model covers four startup modes on the three validated architectures: explicit poll first, direct keygen first, old CLI no `.rnd`, and CLI with `.rnd`. The first two modes also run on synthetic big-endian 64-bit. These modes are alternatives, not additive candidate probabilities.

## 3. Enumeration and result

**(a)** Exact space: PID **1–32,767**, four PID/counter architecture encodings (`le64`, `le32`, `be32`, synthetic `be64`), 16 consecutive successful secp256k1 keygens per PID, offsets **0–15**. There are 14 architecture × startup paths: four for each validated architecture and two for synthetic `be64`. Each keygen includes its own `RAND_add(time_t)` and one or more 32-byte `RAND_bytes` calls if BN range rejection occurs. The public point is serialized compressed for set lookup, and on a hit the uncompressed point is compared to the CSV. Only public match metadata would be written; candidate scalars are never saved. The 21,953 targets are unique, valid uncompressed points in this CSV. The 14 worker receipts record completion independently; [result.json](result.json) sums them and pins the CSV SHA-256 **after CRLF-to-LF normalization**, matching the committed Git blob on both Windows and Unix checkouts.

**(a; bounded null)** The completed screen found **zero matches in 7,339,808 candidate keygen slots** (`14 × 32,767 × 16`) against all 21,953 targets. Slots are not asserted to be distinct public keys. This means the CSV points do not occur in the enumerated space under the modeled startup paths. It does not establish that the keys were generated securely or on a particular operating system. No hit required a live-chain check, and no chain API was queried for this follow-up.

## 4. Exact limits and reproduction

**(a)** Untested: PID **0** or **≥32,768** (including raised `pid_max`); offsets **≥16**; any preceding calls such as arbitrary `RAND_bytes`, wallet/key-generation, file/environment seeds, or process/thread/fork sequences outside the four modeled paths; alternative `RAND_METHOD`s, OpenSSL versions or patches with different state transitions; non-Linux ABI layouts, unusual `pid_t` widths, MIPS-specific behavior and unvalidated big-endian 64-bit paths. The vector-validated paths are historical examples, not an exhaustive list of process states. Thus “zero matches” cannot be extrapolated to every Debian-weak key. In particular, PIDs and stream offsets are not the only variables.

**(a)** Reproduction from the repo root (run here with Python 3.12.14 and `cryptography` 50.0.1):

```powershell
python scripts/debian_weak_screen.py vectors --download-vectors
python scripts/debian_weak_screen.py scan
python scripts/debian_weak_screen.py aggregate
python scripts/debian_weak_screen.py manifest
```

The `scan` command checkpoints each architecture/path by PID in ignored `analysis/phase3/cache/debian/` and resumes without repeating a completed checkpoint. Each worker stops if any one detects a match and leaves only public metadata in `hit_pending.json`; the independent on-chain comparison is then required before any claim. The published validation PEMs and the raw source/corpus research downloads remain in ignored local cache, while code and checksummed receipts are committed. The screen is analytical only: it constructs, signs and broadcasts no Bitcoin transaction.
